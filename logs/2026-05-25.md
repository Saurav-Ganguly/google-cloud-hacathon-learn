### Phase A — Reference doc rewrite

The existing [[concepts/adk-graph-workflows]] was a thin stub written
before the docs were available. Rewrote end-to-end against the pasted
docs. Now covers:

- `Workflow` class + `edges` array shape (incl. the `"START"` rule
  and multi-`START` parallel kickoff).
- The `Event` class as the data bus — `output`, `message`, `state`,
  `route` parameters, `yield` vs `return` semantics, multi-yield
  list semantics.
- Five node kinds: `FunctionNode`, `Agent` (with the
  `mode="single_turn"` requirement), `JoinNode`, `RequestInput`
  (HITL with `message`/`payload`/`response_schema`), and nested
  `Workflow`-as-node (with bubble-up event semantics).
- Edge syntax for sequential / branching / parallel fan-out /
  parallel + join.
- Per-node `input_schema` / `output_schema` (works on FunctionNodes
  too, not just Agents).
- The two instruction-access syntaxes: `{ClassName.field}` for
  unrestricted lookup and `<ClassName.field from source_node>` for
  source-restricted lookup.
- All six cautions, each called out with an explicit `**Caution:**`
  prefix:
  1. `Event.output` is one-per-node (runtime error otherwise).
  2. `Event.state` is for tiny scalars only.
  3. `JoinNode` hangs on any incomplete upstream — emit a failsafe.
  4. Agents inside graphs MUST be `mode="single_turn"`.
  5. Live Streaming is not compatible with graphs.
  6. Some third-party integrations are not compatible.
- A dedicated `VERIFY ON BUILD` section enumerating the import-path
  unknowns to resolve in the next sandbox session (`Workflow`,
  `Event`, `JoinNode`, `RequestInput`, `mode` parameter name,
  `Context` import).

Also fixed the previous note's wrong URL prefix
(`adk.dev/workflows/...` → `adk.dev/graphs/...`).

### Phase B — Tutorial sibling file

New file: [[concepts/adk-graph-workflows-tutorial]] (~430 lines).
Single end-to-end worked example: a **support ticket triage
workflow** — load → classify → router → three nested branches
(BUG / SUPPORT / LOGISTICS) → human approval gate → post reply.

Decision recap (asked the user during planning):
- Location: sibling file in `concepts/` (not embedded in the ref doc,
  not in a new `tutorials/` folder).
- Style: one complete worked end-to-end example with every concept
  called out inline.

Concepts exercised, in order they appear:
1. `Workflow` skeleton + `edges` array.
2. `FunctionNode` (`load_ticket`).
3. `Agent` node with `input_schema`, `output_schema`,
   `mode="single_turn"`.
4. `FunctionNode` emitting `Event(route=...)`.
5. Branching dict.
6. Nested `Workflow` for each branch.
7. `input_schema` on a FunctionNode receiving typed input.
8. `<ClassName.field from source_node>` source-restricted instruction
   syntax in `write_apology`.
9. `Event(output=...)` and the one-per-node rule.
10. Side example: parallel fan-out + `JoinNode` (3 enrichment
    agents joined for a drafter) — split off as its own example
    because forcing parallel into a router branch would be artificial
    (router picks one branch, never several).
11. `RequestInput` with `message` + `payload` + `response_schema`.
12. `Event(message=...)` for the user-facing channel.
13. `Event(state=...)` for tiny scalars.
14. `mode="single_turn"` requirement (stated up front, restated in
    the "what would have bitten us" cautions section).
15. Closing cautions reframed as anti-patterns.

The whole workflow is then re-emitted as one fully-annotated code
block at the end ("here is the whole workflow") so the reader can
copy-read top-to-bottom without scrolling.

Ends with a "why a graph here vs `SequentialAgent`?" honest
reflection — the branching + HITL gate are the *only* things tipping
this past a `SequentialAgent`; without either, sequential is simpler.
